# WordPress Plugin Developer Handbook — compliance mapping

Most of the [Plugin Developer Handbook](https://developer.wordpress.org/plugins/)
is architectural guidance — how to use a WordPress API correctly — not a set
of lint rules, so there is no tool that checks "did you register your custom
post type correctly" the way PHPCS checks a docblock. `SECURITY.md` already
does this for the OWASP Top 10; this document does the same for the
handbook's other sections: one row per topic, naming the handbook's actual
rule, where Wynko implements it, and how that's verified — a named
PHPCS/PHPStan sniff where one genuinely applies to the topic, otherwise "read
against the handbook and confirmed" on the date below.

**When it goes stale:** update the relevant row in the same commit that
touches that subsystem, the same way `SECURITY.md`'s OWASP rows are kept
current for new endpoints/handlers.

Last confirmed: 2026-08-25.

| Topic | Handbook rule | Wynko's implementation | Verified by |
|---|---|---|---|
| [Hooks](https://developer.wordpress.org/plugins/hooks/) | Actions perform a task and return nothing; filters accept a value, modify it, and return it, with no side effects. Custom hooks should be prefixed. | Wynko defines its own `wynko_*` actions and filters across the API transport, campaigns, signup forms, activity log, maintenance, and integrations paths — see `docs/hooks.md` for the full reference. `wynko_register_integrations` is the one custom filter whose registered callers are, by design, not limited to Wynko's own code: any active plugin or theme can append an `Integration` to it (see `docs/hooks.md#integrations`), which means a third-party plugin can now trigger a Laposta write via whatever that integration's own `boot()` hooks into — the bundled Contact Form 7 and HTML Forms bridges are the first examples. It also still consumes core hooks (`admin_menu`, `rest_api_init`, `admin_post_*`, `plugins_loaded`, `load-{$hook}`, `plugin_action_links_{$plugin_basename}`, `plugin_row_meta`), wired centrally in `includes/Plugin.php` and `includes/Admin/Menu.php`. | Every custom hook is `wynko_`-prefixed, enforced by `WordPress.NamingConventions.PrefixAllGlobals` (part of the full `WordPress` PHPCS ruleset), and covered by a unit test asserting it fires (or filters) as documented. |
| [Administration Menus](https://developer.wordpress.org/plugins/administration-menus/) | Register via `add_menu_page()`/`add_submenu_page()`; gate on the right capability. | `includes/Admin/Menu.php` is the single chokepoint — one `add_menu_page()` call, then `add_submenu_page()` per entry in `screens()` (Settings, Signup forms, Integrations, Activity log). Every registration uses `Menu::CAP` (`manage_options`). | Read against the handbook and confirmed, 2026-08-25; Integrations screen added 2026-08-29. |
| [Settings API](https://developer.wordpress.org/plugins/settings/) | Use `register_setting()`/`add_settings_section()`/`add_settings_field()` rather than hand-rolled option forms, with a sanitize callback. | `includes/Admin/SettingsPage.php`, `Admin/NotificationsTab.php`, `Admin/SecurityTab.php` all use the standard Settings API calls, rendered via `settings_fields()` + `do_settings_sections()`. Option keys/defaults centralize in `Config.php` + `config/settings.php` per `CLAUDE.md`. | Read against the handbook and confirmed, 2026-08-25. |
| [Metadata](https://developer.wordpress.org/plugins/metadata/) | Prefix meta keys; sanitize before storing. | `includes/Forms/FormData.php` — post meta only (no user meta anywhere), keys built via `Config::form_meta_key()` so every key is centralized and prefixed in one place rather than typed at each call site. | Read against the handbook and confirmed, 2026-08-25. |
| [Custom Post Types](https://developer.wordpress.org/plugins/post-types/) | Register with `register_post_type()`, choosing `public`/`show_ui`/`show_in_rest`/capabilities deliberately rather than accepting every default. | `includes/Forms/PostType.php` registers `wynko_form` as a private, storage-only CPT: `public`, `publicly_queryable`, `show_ui`, `show_in_menu`, `show_in_rest`, `has_archive`, `rewrite`, and `query_var` are all `false`; every post capability maps to `manage_options` as defense-in-depth on top of the admin handlers' own capability checks. | Read against the handbook and confirmed, 2026-08-25. |
| [Taxonomies](https://developer.wordpress.org/plugins/taxonomies/) | Register with `register_taxonomy()` when content needs a classification. | None registered — Wynko has no use for one. | N/A — confirmed absent (`grep -rn register_taxonomy includes/` is empty), 2026-08-25. |
| [Users](https://developer.wordpress.org/plugins/users/) | Check capabilities, not roles; grant least privilege. | 20+ `current_user_can()` call sites across the admin/REST/frontend surface, almost uniformly `manage_options` (`Menu::CAP`); no role or capability registration, no user meta. The one deliberate exception — the public signup submit endpoint, unauthenticated by design — is documented in `SECURITY.md`'s A01 row. | `SECURITY.md`'s A01 row (also serves this topic); read against the handbook and confirmed, 2026-08-25. |
| [HTTP API](https://developer.wordpress.org/plugins/http-api/) | Use `wp_remote_*()`, not raw cURL; check `is_wp_error()`; cache repeated calls via transients. | `includes/Api/Client.php` uses `wp_remote_request()` exclusively, an explicit 15s timeout, and checks `is_wp_error()` immediately, classifying non-2xx responses via `Sanitizer::classify_status()`. `includes/Cache.php` caches campaign/list/field responses via `set_transient()`/`get_transient()` with a configurable TTL, invalidated on save and on the schema migration. | Read against the handbook and confirmed, 2026-08-25. |
| [JavaScript, jQuery and Ajax](https://developer.wordpress.org/plugins/javascript/) | Prefer bundled libraries and the REST API over `admin-ajax.php`; nonce every request. | Blocks (`src/block/`, `src/block-form/`) use `@wordpress/*` packages, no jQuery. `src/admin/forms.js` uses jQuery UI `sortable` for one admin drag-reorder widget only. No `admin-ajax.php`/`wp_ajax_*` anywhere — state-changing operations go through `admin_post_*` actions or the `wynko/v1` REST namespace, both nonce-gated per `SECURITY.md`'s A08 row. | Read against the handbook and confirmed, 2026-08-25. |
| [Cron](https://developer.wordpress.org/plugins/cron/) | Use `wp_schedule_event()` for recurring work; clean up scheduled events on deactivation. | Not used — no `wp_schedule_event()`/`wp_schedule_single_event()` anywhere. The sync feature is manually triggered (`admin_post_wynko_sync`), not scheduled. | N/A — confirmed absent, 2026-08-25. |
| [Internationalization](https://developer.wordpress.org/plugins/internationalization/) | Wrap every user-facing string; declare a `Text Domain` matching the slug; `load_plugin_textdomain()` is unnecessary for WordPress.org-hosted plugins since WP 4.6+ auto-loads translations. | Text domain `wynko-for-laposta` declared in `wynko.php`'s header, no `load_plugin_textdomain()` call (correctly omitted). This is a maintainer-proposed slug submitted to WordPress.org for confirmation (see TECHNICAL_DEBT.md), shortening the slug WordPress.org previously assigned during the first review — the plugin's own directory/namespace/option-key identity is unaffected either way. | `WordPress.WP.I18n` (`phpcs.xml.dist`, configured with `text_domain: wynko-for-laposta`) enforces the domain string on every translation call project-wide; `bin/wp-org-check.sh` cross-checks the header against `phpcs.xml.dist`'s configured value. |
| [Privacy](https://developer.wordpress.org/plugins/privacy/) | Disclose third-party data sharing via `wp_add_privacy_policy_content()`, so it appears as suggested text on **Settings → Privacy**; provide personal-data exporters/erasers if the plugin stores personal data itself. | **Gap found and closed in this change**: Wynko sends every signup's email/field data to Laposta but had never hooked `wp_add_privacy_policy_content()` — the disclosure only existed in `readme.txt`, which a site owner writing their actual privacy policy never sees. `includes/Privacy.php` now registers the suggested text on `admin_init`, reusing the same disclosure language as `readme.txt`'s "External services" section. No exporter/eraser is needed: Wynko stores no personal data in WordPress itself — signup data goes straight to Laposta and is never persisted here (`SECURITY.md`'s A09 row); the only WP-side data is the `wynko_form` CPT's aggregate `signups` counter, an integer with no PII. | Confirmed live: logged into a `wp-env` instance and loaded **Settings → Privacy → Policy Guide**, where the suggested text renders verbatim, 2026-08-25. |
